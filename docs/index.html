Event Driven Architecture

🏠 A small SaaS project for IoT

📌 About This Project

This is a personal project and a proof of concept to learn and implement Event Driven Architecture using Python, RabbitMQ, and Kubernetes.

Builds and workflow status

💡 Main idea

A simple excuse to learn and use Python as Pub/Sub with a message broker, in this case RabbitMQ, to provision infrastructure triggered by events like "buy a small module" and, finally, to monitor all that infrastructure. I love IoT. For this reason, this PoC is designed to simulate a "SaaS product". At the end of all this, it will provision my small IoT modules. 👾

The project has two big "blocks":
● First: Base infrastructure. Kubernetes on AWS EC2, all deployed with Terraform and Ansible.
● Second: Kubernetes architecture: APIs, services, databases and other endpoints, all deployed in Kubernetes with Helm using my own Helm-charts

🔥 Supposed problem


💀 I need to manage a lot of inputs, and each of them will trigger different tasks, like messages, deployments, and more. Obviously I will reuse that data so other jobs can generate custom events, and finally I will use Grafana for analysis and trends.
💀 Some apps have to get information, but a common problem is having or developing a lot of products with different technologies, like Node.js, Python or PHP.
💀 I would like to have a shared source of data, to avoid rebuilding or writing connectors or APIs to connect components written in different technologies/languages.
💀 All developers need to know which version must be fixed, or I need a person to manage the version numbers. (I would like to avoid managing them manually.)

🏁 Objective


● The same scenario must be able to be reproduced multiple times.
● The full project (or almost all of it) must be code (and/or IaC).
● Create a simple API to centralize all "inputs" and organize workloads by queues.
● Each microservice consumes its own queue and, if needed, can consume others too.
● Each microservice does a specific task, to avoid having "JUMBO-Pods".
● All microservices generate logs for future monitoring, analysis, improvements and troubleshooting.
● All logs must be exposed on stdout, to avoid writing data inside the container. This lets me run my pods with a read-only filesystem.
● Automate all tasks via API calls between microservices.
● Gain scalability and security by isolating each task in small actions/calls.
● Avoid tech dependencies or "human-tech dependence". Everyone can enjoy their own tech/language.
● The standard (input/output) will be because it is an open standard and is easy to implement and parse.

TraceID from deployment workflow to pod annotations



This trace_id is super useful when you need to see the deployment trace, and I also use it as a reference tag and/or annotation in pods. The trace_id is generated on the first API call of the deployment process and is attached to all the pods. If you use Grafana or similar, you can trace all the steps and associate them with the deployment, or even with each pod deployed by this process.
